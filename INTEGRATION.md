# TG Analytics — Документация интеграции (API Contract)

Руководство для разработчиков сторонних Telegram-ботов (VPN-сервисы, платные подписки, SaaS-боты) по интеграции с платформой аналитики `TG Analytics`.

---

## 0. Главное в двух абзацах

**Событие всегда принадлежит проекту, и почти никогда — не обязано иметь метку.** Проект (`projectId`) — единственное обязательное измерение: без него аналитика не знает, чью выручку считать. Атрибуция (по рекламной ссылке или по UTM-метке) — необязательна, и её отсутствие не ошибка, а нормальный ответ «человек пришёл сам».

**Событие без метки записывается, а не отбрасывается.** Раньше покупка от пользователя без предыдущего касания отвергалась с `422` — и, поскольку боты ответ не читают, просто исчезала. Теперь она сохраняется с пометкой `source = "organic"` и попадает во все метрики проекта. На дашборде выручка всегда раскладывается на три доли: по ссылкам, по UTM, без метки — и эти три доли обязаны сходиться в общую сумму.

---

## 1. Куда слать и чем подписывать

**Адрес:** `POST https://<ваш-хост-аналитики>/api/events`

**Подпись:** отдельной подписи нет — используется общий секрет в заголовке.

| Заголовок | Значение |
| :--- | :--- |
| `Content-Type` | `application/json` |
| `X-API-Key` | значение `API_SECRET` из окружения аналитики (выдаёт администратор) |

Ключ сравнивается в постоянном времени и один на все серверные интеграции. Он даёт полный доступ к API, поэтому передавать его в браузер или в клиентский код нельзя — только сервер-серверные вызовы.

Ответ `401` означает неверный или отсутствующий ключ. Ответ `422` — что событие не удалось отнести ни к какому проекту (см. §3).

---

## 2. Где взять `projectId`

Один раз, при настройке:

```bash
curl -s https://<хост>/api/projects -H "X-API-Key: <ключ>"
```

Вернётся список проектов с `id`, `name`, `type` и `botUsername`. Возьмите `id` своего проекта и пропишите его в конфигурацию бота — он не меняется.

Типы проектов:

| `type` | Что это |
| :--- | :--- |
| `channel` | Telegram-канал, вход в воронку — подписка на канал |
| `bot_subscription` | Приватка: бот продаёт доступ к каналу |
| `bot_direct` | Бот продаёт свой продукт, канала за ним нет (VPN) |

**Если прописать `projectId` некуда** — передавайте вместо него `botUsername` (свой, без `@`). Аналитика найдёт проект по нему. Это запасной путь: он работает, только если username бота записан в карточке проекта.

## 3. Контракт `POST /api/events`

### Тело запроса

| Поле | Тип | Обязательность | Описание |
| :--- | :--- | :--- | :--- |
| `tgUserId` | `string` | **Да** | Telegram User ID |
| `eventType` | `string` | **Да** | Тип события из словаря ниже |
| `projectId` | `number` | **Да\*** | Чей это трафик. \*Можно опустить, если событие несёт `linkId`/`utmLinkId` или пользователь уже известен аналитике |
| `botUsername` | `string` | Опц. | Замена `projectId`, если его негде хранить |
| `linkId` | `number` | Опц. | Рекламная ссылка кампании, если пользователь пришёл по ней |
| `utmLinkId` | `number` | Опц. | UTM-метка (обычно проще передать slug — см. §5) |
| `amount` | `number` | Для оплат | Сумма в рублях, уже за вычетом скидки — это фактически полученные деньги |
| `promoCode` | `string` | Опц. | Применённый промокод |
| `discountAmount` | `number` | Опц. | Сколько промокод срезал, ₽ |
| `languageCode` | `string` | Опц. | Код языка Telegram (`"ru"`), используется как грубый geo-прокси: реального IP Telegram не отдаёт |

### Как определяется проект и метка

Порядок проверок, сверху вниз, первый сработавший выигрывает:

1. `linkId` в запросе → проект берётся из кампании этой ссылки, `source = "link"`.
2. `utmLinkId` в запросе → проект из метки, `source = "utm"`.
3. **История пользователя** — последнее его событие в этом проекте. Наследуются и метка, и её тип. Так работает атрибуция по последнему касанию: платёж достаётся той кампании, которая привела человека.
4. `projectId` из запроса → `source = "organic"`.
5. `botUsername` из запроса → то же самое.
6. Ничего из перечисленного → `422`, событие не записано.

Шаг 3 намеренно стоит выше шагов 4–5: у вернувшегося покупателя платёж должен остаться за приведшей его кампанией, а не превратиться в органику только потому, что бот не повторил метку. При этом история переносится **только внутри того же проекта** — человек, купивший и в приватке, и в VPN, не утащит кампанию из одного проекта в выручку другого.

### Словарь типов событий

| `eventType` | Когда слать | `amount` | Что делает с метриками |
| :--- | :--- | :--- | :--- |
| `lead` | Пользователь нажал `/start` | Нет | Вход в воронку |
| `trial_start` | Начался пробный период | Нет | Вход в воронку |
| `payment` | Первая успешная оплата | **Да** | Выручка, покупатель |
| `renewal` | Продление подписки | **Да** | Выручка, покупатель |
| `churn` | Отписка / отток | Нет | Учитывается в LTV и оттоке |
| `join` | Вход в канал | Нет | Только для проектов-каналов |

Для бота без канала (`bot_direct`) вход в воронку — это `lead` при `/start`. Никакого `join` там не будет, и все метрики считаются от `lead` и от общего числа увиденных пользователей.

## 4. Порядок вызовов для бота без канала (VPN)

**При `/start` без payload** — человек пришёл сам:

```bash
curl -X POST https://<хост>/api/events \
  -H "Content-Type: application/json" \
  -H "X-API-Key: <ключ>" \
  -d '{
    "projectId": 3,
    "tgUserId": "777000123",
    "eventType": "lead",
    "languageCode": "ru"
  }'
```

**При `/start` с UTM-payload** — см. §5, там отдельная ручка.

**Пробный период:**

```bash
curl -X POST https://<хост>/api/events \
  -H "Content-Type: application/json" \
  -H "X-API-Key: <ключ>" \
  -d '{
    "projectId": 3,
    "tgUserId": "777000123",
    "eventType": "trial_start"
  }'
```

**Оплата** — метку передавать не нужно, она подтянется из истории:

```bash
curl -X POST https://<хост>/api/events \
  -H "Content-Type: application/json" \
  -H "X-API-Key: <ключ>" \
  -d '{
    "projectId": 3,
    "tgUserId": "777000123",
    "eventType": "payment",
    "amount": 299,
    "promoCode": "SEPT20",
    "discountAmount": 75
  }'
```

**Продление** — то же самое с `"eventType": "renewal"`. **Отписка** — `"eventType": "churn"` без `amount`.

`projectId` стоит слать во всех запросах, даже когда он теоретически выводится из истории: это единственное, что гарантирует запись события, если история почему-то пуста.

## 5. UTM-метки

Метка создаётся в дашборде (вкладка «UTM-метки») и принадлежит проекту. Дашборд отдаёт готовый диплинк вида `https://t.me/<бот>?start=<slug>`.

**При `/start` с payload, совпадающим со slug**, вызовите:

```bash
curl -X POST https://<хост>/api/utm/hit \
  -H "Content-Type: application/json" \
  -H "X-API-Key: <ключ>" \
  -d '{
    "slug": "abc12345",
    "tgUserId": "777000123",
    "languageCode": "ru"
  }'
```

Это записывает `lead` с привязкой к метке. Отдельно слать `lead` в `/api/events` в этом случае **не нужно**.

Ответы: `201` — записано (`{"success": true, "recorded": true}`), `404` — такого slug нет. Если `recorded: false`, событие уже было записано раньше — это защита от повторной доставки, а не ошибка.

Дальнейшие события (оплаты, продления) идут обычным путём через `/api/events`: метка подтянется из истории сама.

> Ручка `POST /api/utm/purchase` осталась для совместимости со старыми интеграциями. Она делает то же, что `/api/events`, и тоже больше не теряет покупки без метки — но в новых интеграциях используйте `/api/events`.

## 6. Ограничения и особенности поведения

**Ограничение частоты запросов.** Отсутствует.

**Защита от дублей.** Уникальный ключ — `(projectId, tgUserId, eventType, ts)`, с точностью до секунды. Повторная доставка того же события в ту же секунду не создаст вторую запись и вернёт успех. Обратите внимание: ключ больше не включает ссылку, поэтому два события одного типа от одного пользователя в одну секунду считаются одним даже при разных метках.

**Ответы, которые стоит логировать.** `422` означает, что событие потеряно: в нём не было ни `projectId`, ни `botUsername`, ни метки, и пользователь аналитике незнаком. Это единственный случай, когда данные не сохраняются, и он всегда указывает на недостающее поле в запросе, а не на «неотслеживаемый трафик». Боты обычно шлют события «выстрелил и забыл» — стоит хотя бы писать такие ответы в лог, иначе пропажа будет незаметной.

**Суммы.** `amount` — это полученные деньги, уже за вычетом скидки. Поля `promoCode` и `discountAmount` нужны только чтобы понимать, какие коды работают; выручку они не корректируют.

**Валюта.** Всё в рублях. Если платёж прошёл в другой валюте, конвертируйте на своей стороне.
